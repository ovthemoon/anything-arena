# 아무거나 무기 배틀 — 제품·게임·기술 기획서 v0.1

**가제:** 아무거나 결투장 / Anything Arena  
**작성일:** 2026-09-23  
**문서 상태:** 빌드데이 프로토타입 제안. 구현·배포·성능 검증 전.  
**범위:** 브라우저 기반 1대1 온라인 파티 배틀.

> 무기를 가져오세요. 강한 이유는 저희가 갖다 붙입니다.

지금까지 논의한 핵심은 자유로운 무기 입력, AI 전투 판정, 과장된 중계와 TTS, 타격감, 욕설·인신공격 경고, Cloudflare 기반 온라인 배포다. 아래의 동시 입력 방식, 체력, 피해량, 제한 시간 등은 이를 구현 가능한 형태로 구체화한 **초기 제안값**이다. 플레이테스트 후 조정한다.

## 1. 제품 정의

플레이어 두 명이 일상적인 물건이나 황당한 개념을 무기로 제출한다. 게임은 그 입력을 제한된 능력을 가진 전투 캐릭터로 해석한다. 플레이어는 준비된 기술을 고르거나 자신만의 공격을 짧게 입력한다. AI는 공격의 의미와 상성을 판단하고, 서버 코드는 피해량과 승패를 확정하며, 해설자는 확정된 장면을 비장하게 중계한다.

**핵심 경험은 ‘내가 입력한 이상한 물건이, 내 의도에 맞게 싸우는 장면을 상대와 함께 보는 것’이다.**

| 항목 | 제안 |
|---|---|
| 장르 | 코미디·창의력 기반 온라인 파티 배틀 |
| 인원 | 1대1, 방 코드·초대 링크로 입장 |
| 플랫폼 | PC·모바일 웹, 별도 설치 없음 |
| 언어 | 한국어 우선 |
| 경기 길이 | 무기 준비 이후 약 60~90초를 목표로 조정 |
| 핵심 입력 | 무기 이름, 기술 선택 또는 짧은 공격 문장 |
| 핵심 출력 | 기술명, 타격 연출, 체력 변화, 음성 중계 |
| 초기 이용 장면 | 빌드데이 참가자끼리 대결, 친구 간 짧은 한 판 |
| 초기 목표 | 완성도 높은 한 경기와 재대결 의사 검증 |
| 목표가 아닌 것 | 랭크 경쟁, 엄밀한 물리 시뮬레이션, 무제한 능력 생성 |

### 왜 AI를 사용하는가

우리가 직접 만드는 것은 수많은 무기별 전용 애니메이션이 아니다. 공통 공격 연출과 수치 규칙을 만들고, 입력마다 달라지는 무기 설정·기술 표현·의미 판단·중계를 AI가 구성하도록 제안한다.

‘젖은 양말’과 ‘읽지 않은 메시지 382개’가 같은 돌진 연출을 사용하더라도, 기술명·공격 이유·효과 표현·해설은 달라진다. 자동 이미지 생성은 필수 조건이 아니다.

## 2. 제작 원칙

**재미는 자유롭게, 규칙은 좁게.** 플레이어의 표현은 열어두되, 실제 효과와 피해량은 코드가 허용한 범위만 사용한다.

**AI는 의미를 판단하고, 서버는 숫자를 결정한다.** 모델이 현재 체력, 피해 상한, 승패를 직접 수정하지 않는다.

**공격은 해설을 기다리지 않는다.** 판정이 끝나면 전투를 진행하고, 늦은 음성은 생략한다.

**물건은 놀려도 사람과 가족은 공격하지 않는다.** 입력 검사를 통과하기 전에는 상대 화면이나 TTS에 원문을 노출하지 않는다.

**처음에는 두 사람이 한 판을 끝내는 경험을 완성한다.** 계정, 공개 매칭, 관전, 이미지 생성, 랭킹은 뒤로 미룬다.

## 3. 대표 플레이 장면

### 무기 준비

A는 ‘젖은 양말’, B는 ‘배터리 1% 스마트폰’을 입력한다.

| 구분 | A | B |
|---|---|---|
| 이름 | 젖은 양말 | 배터리 1% 스마트폰 |
| 설명 | 하루 종일 따라다니는 축축함 | 마지막 순간까지 꺼지지 않는 집념 |
| 허용 능력 예시 | 수분 전달, 휘두르기 | 진동, 화면 빛 |
| 약점 예시 | 열에 마름 | 수분에 취약함 |
| 기본 기술 예시 | 축축한 최후의 일격 / 젖은 회전타 | 방전 직전 진동파 / 마지막 화면 섬광 |

이 설정은 설명용 예시다. 실제 경기에서는 생성 후 검증한 설정을 두 사람에게 공개하고, 경기 중에는 변경하지 않는다.

### 첫 라운드

A가 입력한다.

> 젖은 양말을 휘둘러 스마트폰의 충전 단자를 축축하게 만든다.

B는 ‘방전 직전 진동파’를 선택한다.

서버가 두 행동을 같은 라운드 시작 상태로 평가한다. 예를 들어 A는 약점 활용으로 40 피해, B는 일반 공격으로 30 피해가 확정됐다고 가정한다.

화면에서는 A의 기술명 등장 → 양말 돌진 → 충돌 정지 → 물방울 이펙트 → B 체력 감소를 먼저 보여준다.

> “충전 단자까지 젖었습니다!”

이어서 스마트폰의 진동 공격과 A의 피격을 보여준다.

**라운드 결과: A 70 / B 60.** 연출 순서와 관계없이 양쪽 행동은 모두 적용한다. 이 버전의 물방울은 시각 표현이며, 별도의 지속 피해나 충전 봉쇄 효과는 아니다.

## 4. 경기 진행 방식

### 4.1 한 경기 흐름

방 만들기 → 상대 초대 → 무기 입력 → 검사·설정 생성 → 설정 확인 → 3개 라운드 → 결과 → 재대결.

한 라운드는 **동시 비공개 입력 → 판정 확정 → 두 공격 순차 연출 → 다음 라운드**로 진행한다.

앞서 논의한 턴제 방향을 유지하되, 서로의 입력을 기다리는 시간을 줄이기 위해 두 사람이 같은 입력 구간에 행동을 결정하는 안이다. 공격 문장은 양쪽 확정 전까지 상대에게 공개하지 않는다.

### 4.2 기본 규칙

| 항목 | 초기 제안값 |
|---|---|
| 시작 체력 | 양쪽 100 |
| 라운드 수 | 최대 3라운드 |
| 행동 기회 | 매 라운드 양쪽 1회, 경기당 최대 6개 공격 |
| 행동 입력 시간 | 라운드당 15초 |
| 입력 조기 종료 | 양쪽 행동이 모두 승인되면 즉시 판정 단계로 이동 |
| 공격 선택 | 생성된 기술 2개 또는 직접 입력 |
| 직접 입력 길이 | 최대 60자, 클라이언트·서버 동일 기준 |
| 입력 미완료 | 제한 시간이 끝나면 코드에 정의한 기본 공격 적용 |
| 확률 요소 | 첫 버전에는 명중·회피·치명타 난수 없음 |
| 피해량 | 제한 20 / 일반 30 / 강력 40 |
| 판정 기준 | 고정된 무기 능력과 약점, 제출된 공격의 관계 |
| 승패 | 라운드 정산 후 KO 확인, 3라운드 종료 시 남은 체력 비교 |
| 동점 | 무승부, 연장전 없음 |
| 동일 라운드 동시 KO | 무승부 |

**선공 보너스는 없다.** 먼저 연출된 공격으로 체력이 0이 되더라도 같은 라운드에 확정된 상대 공격을 취소하지 않는다. 연출 선후는 번갈아 표시할 수 있지만 결과에는 영향을 주지 않는다.

피해량 20/30/40과 체력 100을 사용하므로, 정상적인 수치 규칙에서는 첫 두 라운드 안에 KO가 발생하지 않는다. 첫 테스트에서는 3라운드 분량을 확보하는 쪽을 의도한다.

### 4.3 기본 공격과 재입력

입력하지 않았거나 시스템 장애로 자유 입력을 승인하지 못하면, **미검사 문장을 사용하는 대신** 코드에 정의한 ‘기본 공격’으로 교체한다. 기본 공격은 30 피해이며, 생성된 두 기술과 별개의 안전한 대체 행동이다.

각 플레이어의 신규 자유 입력 판정 요청은 라운드당 최대 2회로 제한한다. 같은 actionId의 네트워크 재전송은 새 요청으로 세지 않는다. 거절 후 수정은 남은 시간 안에서만 가능하며, 거절됐다고 입력 시간을 늘리지 않는다.

입력 마감 직전에 접수된 검사 요청에는 최대 1.5초의 서버 처리 유예를 둔다. 유예가 끝나도 승인되지 않으면 기본 공격으로 바꾼다. 늦게 온 결과는 해당 actionId의 유효성을 확인해 폐기한다.

### 4.4 상태 이상 범위

첫 버전은 물방울, 전기, 흔들림 같은 **시각 태그만** 제공한다. 기절, 다음 턴 건너뛰기, 회복, 지속 피해, 방어력 증감 등 실제 수치를 바꾸는 상태 이상은 다음 버전으로 미룬다.

중계에서도 구현되지 않은 상태 이상이 적용됐다고 말하지 않도록 제한한다.

## 5. 무기 생성과 능력 범위

### 입력

닉네임 12자, 무기 이름 30자, 선택적 특징 설명 50자를 초기 상한으로 둔다. 판정 기준이 같은 문자 수 계산기를 클라이언트와 서버가 공유하고, 요청 바이트 크기도 별도로 제한한다.

회원가입이나 사진 업로드 없이 시작한다. 무기 이름은 사물뿐 아니라 ‘월요일 아침’, ‘읽지 않은 메시지’ 같은 추상 소재도 허용한다. 다만 모든 소재는 경기 시작 때 제한된 전투 능력으로 변환한다.

### 생성 결과

한 무기에는 한 줄 소개, 능력 최대 2개, 약점 1개, 준비된 기술 2개, 정해진 목록 중 시각 태그를 부여한다. 모든 무기의 체력과 피해 상한은 같다.

‘모든 것을 없애는 신’을 입력해도 즉사 권한을 주지 않는다. 예를 들어 ‘위압감’과 ‘빛 방출’ 같은 허용 능력으로 해석하고 그 결과를 공개한다. 플레이어는 확정된 설정을 확인한 뒤 시작한다.

경기 중 새 능력을 주장해도 무기 설정을 확장하지 않는다. 새로운 무기로 바꾸려면 재대결에서 다시 입력한다.

### 준비된 기술

생성된 기술은 단순한 기술명이 아니라, 완성된 공격 설명과 공통 연출 유형을 함께 가진다. 상대 무기가 확정되면 검증·판정 결과를 준비 단계에 저장한다. 같은 경기, 같은 상대, 같은 규칙 버전에서 같은 기술을 선택할 때는 이 결과를 재사용한다.

캐시는 경기·무기 버전·상대·행동·판정 규칙 버전·안전 정책 버전을 포함한 키로 구분한다. 다른 상대에게 얻은 판정을 그대로 재사용하지 않는다.

설정 생성에 실패하면 실패 사실을 안내하고, 사전에 검수한 기본 무기 두 개로 진행할 수 있게 한다. 임의 입력을 이해한 것처럼 위장하지 않는다.

## 6. AI 역할과 Jev 판정

### 역할 분리

| 구성 | 담당 | 금지 |
|---|---|---|
| 설정 생성 LLM | 무기 설명·능력·약점·기술 구성 | 코드 실행, 무제한 능력·피해량 부여 |
| Jev | 입력 허용 여부, 공격 적합성·상성·연출 분류 | 현재 HP·최종 승패 직접 수정 |
| 전투 엔진 | 피해량, 동시 정산, 라운드, 경고 처분 | 자연어의 의미를 임의로 추측 |
| 중계 LLM | 확정된 사건에 맞는 짧은 해설 | 판정 뒤집기, 새 효과·수치 발명 |
| TTS | 검사된 대사 음성화 | 원문 자동 재인용, 별도 내용 생성 |

TypeSafe의 Choice는 정의한 선택지에 대한 분류 결과와 확률 분포를 반환하며, 여러 질문을 한 요청에 묶어 병렬 평가할 수 있다. 실제 응답은 어댑터에서 내부 게임 데이터로 변환한다. 아래 형식은 Jev의 실제 API 응답을 그대로 묘사한 것이 아니다.[^S01]

### 판정 질문

| 필드 | 내부 선택지 예시 |
|---|---|
| moderation | ALLOW / REWRITE / FOUL / UNCERTAIN |
| validity | VALID / OUTSIDE_CAPABILITY / SYSTEM_INSTRUCTION |
| effectiveness | LIMITED / NORMAL / STRONG |
| animation | DASH / PROJECTILE / SHOCKWAVE / PSYCHIC |
| reasonCode | WEAKNESS_MATCH / RESISTANCE_MATCH / OFF_THEME / NORMAL |

요청에는 고정된 두 무기의 설정, 해당 공격, 규칙 버전만 보낸다. 공개되지 않은 상대의 이번 공격은 보내지 않는다. 입력 문장은 신뢰할 수 없는 게임 데이터로 구분하고, 모델 지시문이나 도구 실행 명령으로 취급하지 않는다.

다중 질문 결과 중 하나가 반칙이라고 해서 나머지 결과가 자동으로 무효화되는 것에 의존하지 않는다. **코드가 안전 판정을 먼저 확인하고, 통과하지 못한 요청의 전투 판정은 폐기한다.**

### 수치 적용

- LIMITED: 고정된 능력과의 연결이 약하거나, 명시된 저항에 막히는 공격. 20 피해.
- NORMAL: 무기 설정에 맞는 일반 공격. 30 피해.
- STRONG: 고정된 상대 약점을 명확하게 활용하는 공격. 40 피해.

능력 범위를 벗어난 주장은 강력 판정으로 승격하지 않는다. 시스템 프롬프트를 바꾸거나 체력을 조작하라는 입력은 명령으로 실행하지 않고 기본 공격으로 대체한다. 이는 곧바로 인신공격 경고에 해당하지는 않는다.

최종 계산은 `상대 HP = max(0, 라운드 시작 HP - 확정 피해량)`이다. 유효하지 않은 열거값, 누락 필드, 모순된 결과는 검증 실패로 처리한다.

`confidence`는 명중률이나 피해 배율로 사용하지 않는다. TypeSafe 문서에 따르면 이는 응답 확률 분포가 얼마나 집중돼 있는지 요약한 값이다. 안전 분류와 전투 분류의 기준도 따로 검증한다.[^S02]

### 모델 선정 원칙

특정 텍스트 모델의 우열이나 한국어 지연은 확정하지 않는다. `TEXT_MODEL`, `JEV_MODEL`, `TTS_MODEL`, `PROMPT_VERSION`을 설정값으로 분리한다. 구조화된 출력은 무기 데이터 생성에 사용하되, 형식 검증과 게임 규칙 검증을 별도로 수행한다. Gemini API는 구조화된 출력과 JSON Schema의 지원 범위를 문서화하고 있다.[^S03]

Jev는 한국어 전투·안전 판정의 초기 후보이며 정확도를 보장하지 않는다. 한국어 평가 세트를 통과하기 전에는 행사 공개판의 자유 입력을 제한하고, 사전 검수된 기술 모드로 시연할 수 있도록 한다.

## 7. 중계와 TTS

### 중계의 성격

‘대상은 하찮지만 해설은 세계대회 결승전’이라는 톤을 유지한다. 공격당 짧은 한 문장, 무기 특성과 실제 발생한 장면 중심으로 작성한다.

좋은 방향은 ‘충전 단자까지 젖었습니다!’처럼 이미 확정된 공격을 재미있게 표현하는 것이다. 실제로 없는 회피·회복·기절·즉사를 선언하거나, 사용자를 무시하는 대사는 금지한다. 피해량과 남은 체력 같은 핵심 정보는 코드가 별도로 표시한다.

### 첫 버전의 음성 범위

맞춤 TTS는 공격당 결과 중계 1회, 경기당 최대 6회로 제한한다. 기술명은 우선 큰 자막으로 보여주고, 기합·심판 호루라기·라운드 안내는 사전 제작된 짧은 음성을 사용한다. 맞춤 기술 선언 음성은 확장 항목이다.

TTS의 초기 비교 후보는 한국어를 지원하는 `eleven_flash_v2_5`다. 공식 문서의 약 75ms 수치는 애플리케이션과 네트워크 지연을 제외한 값이므로, 제품의 종단간 응답 목표로 그대로 사용하지 않는다.[^S04]

### 생성·재생 흐름

전투 결과 저장 → 짧은 해설 생성 → 전체 문장 안전·사실 일치 검사 → TTS → 양쪽에 동일 오디오 제공.

한 사건의 음성은 서버에서 한 번 생성해 공유한다. 브라우저 두 대가 각자 TTS를 호출하지 않는다. 짧은 완성 음성을 R2에 저장하고, 경기 권한을 확인하는 동일 출처 HTTP 경로로 제공하는 구성을 제안한다. R2는 Workers 바인딩을 통한 읽기·쓰기를 지원한다.[^S11]

첫 버전은 오디오 스트림을 여러 클라이언트에 실시간으로 복제하는 기능까지 만들지 않는다. 효과음과 자막은 먼저 재생하고, 음성이 해당 장면의 재생 구간 안에 준비될 때만 사용한다.

모든 대사와 음성에는 matchId와 eventId를 붙인다. 해당 장면을 지나쳤거나, 재접속했거나, 재대결이 시작됐으면 오래된 음성을 재생하지 않는다. 한 시점에는 해설 하나만 재생하고, 큐를 무한히 쌓지 않는다.

### 오디오 UX

첫 화면에 ‘소리 켜고 입장’과 ‘소리 없이 입장’을 제공한다. 브라우저 자동 재생 정책상 사용자 상호작용 없이 시작한 소리가 차단될 수 있으므로, 클릭 시 오디오를 활성화하고 실패 시 재생 버튼을 표시한다.[^S05]

행사장에서 같은 화면을 함께 보는 경우를 위해 ‘공용 화면만 소리 재생’ 옵션을 둔다. 자막은 음성 사용 여부와 관계없이 제공한다. 실제 인물의 목소리 복제는 사용하지 않고, 사용 권한이 확인된 음성·효과음을 선택한다.

### 기본 문구

‘엄마’라는 단어만으로 차단하지 않는다. 예를 들어 ‘엄마의 잠깐 와봐’라는 허구적 무기와, 실제 참가자의 가족을 비하하는 문장을 구분한다.

### 처분

명확한 반칙 1회에는 노란 카드와 고정 안내를 표시하고, 시간이 남으면 수정할 수 있다. 같은 경기에서 2회가 되면 자유 입력을 종료하고 준비된 기술만 사용하게 한다. 반칙으로 체력을 깎거나 즉시 패배시키지는 않는다.

> 삐익! 인신공격 반칙입니다. 무기로 승부하세요.

같은 actionId를 중복 수신해도 경고는 한 번만 누적한다. 별도 과금·계정 제재·영구 차단은 초기 범위에 없다. 반복 요청이나 자동화 공격은 이용 제한과 호출 제한으로 다룬다.

### 적용 지점

닉네임, 무기명, 특징 설명, 자유 공격, 생성된 설정·기술명·중계까지 검사한다. 생성 출력 문제로 플레이어에게 반칙 경고를 주지 않는다.

검사 전 원문은 작성자 자신의 입력창에만 남는다. 상대 화면, 경기 기록 공개 영역, TTS로 먼저 전송하지 않는다. 경고 음성도 차단한 문장을 인용하지 않는다.

안전 검사와 전투 판정을 한 요청에 묶었는데 그 요청 자체가 실패했다면, 안전 검사를 통과한 것으로 간주하지 않는다. 원문을 숨기고 검수된 기본 공격으로 진행한다.

금칙어 목록과 정규화는 1차 방어다. 초성, 띄어쓰기, 오타, 돌려 말하는 모욕, 무해한 포함 단어를 한국어 테스트 세트에 넣는다. 미탐지와 과차단을 둘 다 기록한다.

## 9. 비주얼과 타격감

### 화면 방향

두 개의 캐릭터 카드가 마주 보는 과장된 중계 화면이다. 어두운 경기장 배경, 선명한 체력 바, 큰 기술명, 단순한 아이콘·실루엣을 사용한다. 장문의 채팅창보다 전투 장면이 화면의 중심이어야 한다.

입력 소재마다 별도 그림을 생성하지 않는다. 미리 준비한 범용 아이콘과 색상·형태 태그를 조합하고, 이름을 크게 표시한다.

### 공통 공격 연출

| 유형 | 연출 |
|---|---|
| 돌진 | 카드 압축 → 전진 → 충돌 → 복귀 |
| 투사체 | 에너지·물방울 등의 도형 발사 → 충돌 |
| 충격파 | 원형 파동 → 상대 카드 흔들림 |
| 정신 공격 | 문자·잔상·노이즈 → 피격 반응 |

네 유형 모두 같은 피해 체계를 사용한다. 유형 자체로 추가 수치 이득을 주지 않는다.

### 한 번의 공격 연출

기술명 등장 → 짧은 준비 동작 → 돌진·투사체 → 충돌 순간 약 60~100ms 시각적 정지 → 효과음·피격 → 체력 바 감소 → 짧은 중계.

이 수치는 초기 연출 제안이며 실측 결과가 아니다. 한 공격의 재생 구간은 최대 약 3초를 기준으로 조정한다. 서버 로직은 시각적 정지에 맞춰 멈추지 않는다. 화면에 보이는 체력 변화는 애니메이션이지만 최종 체력의 기준은 서버가 보낸 값이다.

강한 화면 흔들림을 끄는 옵션과 자막·음소거를 제공한다. 섬광을 과도하게 사용하지 않는다. 처음에는 맵과 스킨 수보다 공격 한 번의 완성도를 우선한다.

## 10. 지연 목표와 실패 처리

다음은 출시 성능 주장이 아니라 **측정할 제품 목표**다. 한국 현장 네트워크, 실제 모델 계정과 부하에서 검증한다.

| 구간 | 초기 목표 또는 상한 |
|---|---|
| 버튼 클릭에 대한 로컬 반응 | 약 100ms 이내 접수 표시 |
| 신규 자유 공격 검사·판정 | P95 1.5초 이내를 목표로 측정 |
| 판정 마감 | 입력 마감 후 최대 1.5초 추가 유예 |
| 한 공격의 연출 | 약 3초 이내 |
| 전투 결과 확정 후 음성 준비 | 해당 공격의 재생 구간 내 제공을 목표로 측정 |
| 무기 준비 | 약 8초 안에 완료·대체 선택 안내를 목표로 측정 |
| 경기 길이 | 준비 이후 약 60~90초 목표 |

P95는 측정 요청 중 95%가 그 시간 안에 완료됐다는 지표다. 평균 지연만 보지 않고 늦은 응답과 대체 행동 비율을 함께 본다.

| 실패 | 처리 |
|---|---|
| 안전 검사 실패·시간 초과 | 미검사 원문 비공개, 기본 공격 대체, 경고 없음 |
| 안전 통과 후 전투 분류만 불확실 | 일반 판정 30 또는 코드 기본 공격 적용, 별도 기록 |
| 설정 생성 실패 | 검수된 기본 무기로 진행할 선택 제공 |
| 중계 생성·검사 실패 | 검수된 고정 중계 사용 |
| TTS 실패·지연 | 자막·기본 효과음으로 진행, 전투는 계속 |
| 늦게 도착한 지난 라운드 결과 | matchId·roundId·actionId 확인 후 폐기 |
| 일시적 연결 끊김 | 상태 복구 지원, 진행 중 입력 시간은 기본 규칙 유지 |
| 장시간 미복귀 | 30초 복귀 유예 이후 경기 중단, 승자 미산정 |

두 플레이어가 모두 떠나도 오래된 방을 영구 유지하지 않는다. 서버 장애가 있었는데 AI 판정이 정상 작동한 것처럼 표시하지 않는다. 사용자 화면에는 ‘연결 지연으로 기본 공격을 사용했습니다’처럼 짧게 알린다.

## 11. 화면 구성

### 시작 화면

게임명, 예시 무기 두 개, 한 줄 설명, 방 만들기, 코드로 참가, 소리 설정. 가입이나 긴 튜토리얼은 없다.

### 대기실·무기 화면

초대 링크·방 코드·QR, 두 좌석 상태, 닉네임과 무기 입력, 생성된 무기 카드, 능력과 약점, 준비 버튼. 상대의 검사되지 않은 입력은 보이지 않는다.

### 배틀 화면

상단에 라운드와 입력 제한 시간, 중앙에 양쪽 캐릭터와 체력, 하단에 기술 버튼 두 개·직접 입력·제출 버튼을 배치한다. 상대가 준비했는지만 보여주고, 상대의 미공개 행동 내용은 숨긴다.

공격 연출 때에는 입력 영역을 접고 전투 장면을 강조한다. 종료된 사건의 해설이 다음 입력과 충돌하지 않게 한다.

### 결과 화면

승자 또는 무승부, 최종 체력, 두 무기, 가장 강했던 확정 공격, 재대결 버튼을 보여준다. 하이라이트 선정은 첫 버전에서는 최고 피해량·동점 시 사건 순서로 처리하고, 추가 LLM 평가를 호출하지 않는다.

재대결은 양쪽 동의 후 새 matchId로 시작한다. 경고와 경기 상태는 새 경기로 초기화하고, 서비스 차원의 호출 제한은 초기화하지 않는다.

## 12. 기술 아키텍처

### 기본 구성

| 구성 | 제안 역할 |
|---|---|
| 웹 클라이언트 | TypeScript 기반 UI, 2D 카드 연출, 오디오·자막 |
| Cloudflare Workers | 정적 파일, HTTP API, 권한 검사, AI 호출 경로 |
| BattleRoom Durable Object | 방·경기 상태, 참가자·행동·피해·승패의 기준 |
| WebSocket | 준비 상태, 라운드 결과, 중계 이벤트 전송 |
| DO SQLite 저장소 | 경기 스냅샷, 처리된 행동, 경고·마감 시각 |
| R2 | 공유할 짧은 음성 파일 |
| 외부 AI 어댑터 | Jev, 설정·해설 모델, TTS 연동 |

프론트엔드는 React + Vite를 초기 구현 선택으로 제안한다. 전투 표현은 DOM/CSS 또는 작은 Canvas 영역으로 시작한다. Unity 클라이언트는 기존 에셋을 반드시 재사용해야 할 때 별도 판단하고, 첫 웹 배포에는 포함하지 않는다.

Cloudflare Workers Static Assets는 정적 화면과 Worker 코드를 한 번의 배포로 올리는 구조를 지원한다. API·WebSocket 경로가 SPA 화면으로 잘못 연결되지 않도록 라우팅을 분리한다.[^S06]

Durable Objects는 고유한 식별자와 강한 일관성의 자체 저장소를 가지며, 여러 클라이언트를 조율하는 용도로 제공된다. **방 하나당 BattleRoom 하나**를 배정하는 구성을 채택한다.[^S07]

### 서버 권위

브라우저는 ‘어떤 행동을 제출했는가’만 전송한다. 피해량·체력·경고 횟수·승자는 클라이언트가 지정할 수 없다. 서버는 유효한 참가자와 라운드를 확인한 뒤 처리한다.

프레임별 위치와 물리를 동기화하지 않는다. 서버는 확정된 사건과 상태를 전송하고, 각 브라우저는 공통 연출을 로컬로 재생한다. 초기 목표는 프레임 단위 동시성이 아니라 사건 순서와 최종 상태의 일치다.

### 영속성·Hibernation

WebSocket Hibernation을 사용하는 방향으로 구현한다. Cloudflare 문서상 유휴 객체가 메모리에서 내려가도 WebSocket 연결을 유지할 수 있지만, 메모리 상태는 초기화된다. 따라서 체력·라운드·행동·마감 시각을 메모리에만 보관하지 않는다.[^S08]

경기 상태와 ‘이미 적용한 roundId’를 원자적으로 저장한 뒤 결과를 전송한다. 재접속 시에는 최신 스냅샷과 eventSeq를 보내고, 지난 타격음·중계를 재생하지 않는다.

### 외부 호출과 중복 처리

AI 호출 전 pending action을 저장한다. 응답 후에는 해당 matchId·roundId·actionId와 행동 상태가 여전히 유효한지 재검증한다. 다른 참가자의 준비 상태 변경만으로 무효화하지 않으며, 지난 경기·이미 대체된 행동은 반영하지 않는다.

외부 API를 기다리는 동안 방 전체를 잠그지 않는다. Cloudflare 문서도 외부 입출력을 포함한 긴 blockConcurrencyWhile 사용을 피하고 버전·상태 검증을 적용하도록 설명한다.[^S09]

원칙은 ‘경기 상태에는 중복 적용이 없어야 한다’이다. 외부 모델 사업자의 요청 처리·과금까지 exactly-once로 보장한다고 주장하지 않는다. 요청 ID와 제한된 재시도를 기록한다.

### 제한 시간

클라이언트 타이머는 표시용이다. 서버가 저장한 deadlineAt이 기준이며, 들어오는 메시지마다 만료 여부를 검사한다. Durable Object Alarm은 방을 깨워 만료 처리를 수행하는 보조 경로로 사용한다.

Alarm은 객체당 한 번에 하나이며 at-least-once 실행 특성이 있다. 입력 마감·판정 유예·재접속 유예·방 만료 중 다음 시각을 예약하고, 실행 시 이미 처리된 항목을 다시 적용하지 않게 만든다. 프레임 단위 정확성을 가정하지 않는다.[^S10]

## 13. 상태와 이벤트 계약

### 경기 상태

`LOBBY → PREPARING → ROUND_INPUT → ROUND_RESOLVING → ROUND_PLAYBACK → 다음 ROUND_INPUT 또는 FINISHED → CLOSED`

연결 상태와 플레이어별 행동 상태는 경기 단계와 별도 필드로 둔다. 플레이어 행동은 NONE, VALIDATING, ACCEPTED, REJECTED로 구분한다. 검사 중 제출 취소·수정은 초기 버전에서 지원하지 않는다. 거절 후에만 남은 횟수와 시간 안에서 새 actionId로 재입력한다.

### 클라이언트 → 서버

| 메시지 | 주요 필드 |
|---|---|
| weapon_submit | requestId, 무기 입력 |
| ready | matchId |
| action_submit | matchId, roundId, actionId, techniqueId 또는 text |
| request_snapshot | matchId, lastEventSeq |
| rematch_ready | matchId |

playerId와 공격 대상은 서버 인증 정보와 좌석에서 결정한다. 클라이언트의 playerId 주장만으로 권한을 인정하지 않는다.

### 서버 → 클라이언트

| 메시지 | 의미 |
|---|---|
| room_snapshot | 공개 가능한 최신 상태 |
| round_started | roundId, deadlineAt |
| action_pending / action_accepted | 본인 입력 접수·승인 |
| opponent_ready | 상대 준비 여부만 공개 |
| input_rejected | 사유 코드·재입력 가능 여부, 본인에게 전송 |
| foul_warning | 고정 안내·누적 경고, 원문 없음 |
| round_resolved | 두 공격, 피해, HP 전후, 연출 순서 |
| commentary_ready | eventId, 검사된 자막·음성 경로·유효 구간 |
| match_finished | 최종 상태·승자 또는 무승부 |
| match_aborted | 연결 장애 등으로 경기 중단 |

전투 사건에는 matchId·roundId·eventId·eventSeq·rulesetVersion을 부여한다. 순서가 빠지거나 상태가 의심스러우면 스냅샷을 요청한다. 경기 종료와 재대결을 구분하기 위해 roomId만으로 이벤트를 식별하지 않는다.

## 14. 권한·비용·데이터 운영

### 익명 참가 권한

방 코드와 초대 링크는 방을 찾는 수단이다. 플레이어 조작 권한은 서버가 발급한 별도 임시 세션으로 관리한다. 같은 출처의 Secure·HttpOnly 쿠키 등을 사용하고, WebSocket 연결의 Origin과 세션을 검증한다. 공유 URL에 플레이어 비밀 토큰을 넣지 않는다.

한 좌석의 중복 연결은 정책을 명확히 한다. 초기 버전은 새로 인증한 연결이 기존 연결을 대체하는 방식으로 제안한다. 새 좌석 배정과 같은 좌석 재접속을 구분한다.

API 키는 Workers Secrets에 저장하고, 저장소·브라우저 번들·공개 로그에 넣지 않는다. Workers는 암호화된 Secret 바인딩을 지원한다.[^S12]

### 호출 제한

방 생성, 무기 재생성, 행동 제출, 중계 생성에 각각 상한을 둔다. 정상 3라운드 경기에서 최대 6개의 공격 사건, 최대 6개의 맞춤 중계와 TTS를 생성한다. 신규 자유 입력 판정은 수정 요청 포함 최대 12회다. 무기 생성·사전 기술 판정·출력 안전 검사 호출은 별도로 계산한다.

공격당 전투 판정 자동 재시도는 초기 버전에서 하지 않고 대체 행동을 사용한다. 설정 생성 재시도는 최대 1회, 해설·TTS 실패는 고정 표현으로 대체한다. 모든 경로에서 재시도는 동일 예산에 포함한다.

방별 제한 외에 계정 전체 일일 AI 호출 예산과 동시 처리 한도를 설정한다. 관리자에게는 신규 방 생성 중지·자유 입력 중지·TTS 중지 스위치를 제공한다. 공개 배포 전 실제 계정의 사용 한도와 제한 작동을 확인한다.

비용 산식은 다음과 같이 관리한다.

`경기 비용 = 설정 생성 + 입력/출력 검사 + 신규 전투 판정 + 해설 생성 + 음성 생성 + 인프라/저장 비용`

아직 경기당 금액은 산정하지 않는다. 샘플 경기의 입력·출력 토큰, 음성 문자·시간, 저장 요청을 실제 사업자 요율에 대입해 확인한다.

### 데이터

입력 텍스트가 판정·음성 생성 목적의 외부 API로 전달된다는 안내를 제공한다. 실명·연락처 등 개인정보 입력을 유도하지 않는다.

방은 10분 비활성 시 닫는 것을 초기 기준으로 하고, 종료된 경기·음성은 짧은 보존 기간 후 삭제한다. 예시 운영 기준은 24시간이며, 즉시 삭제와 동일하다고 표현하지 않는다. R2에는 수명 주기 삭제 정책도 적용할 수 있지만, 실제 정리 완료 시점은 별도로 확인한다.[^S13]

차단된 욕설 원문은 일반 로그에 남기지 않는다. 사유 코드, 모델·프롬프트 버전, 지연, 대체 처리 여부를 중심으로 기록한다. 공개 공유 갤러리는 첫 버전에서 제공하지 않는다.

업무를 나눈다면 서버·규칙, 프론트·연출, AI·안전 평가 세 작업 묶음으로 구분한다. 인원과 일정을 가정하지 않으며, 혼자 진행할 때도 같은 모듈 경계를 유지한다.

## 17. 테스트와 성공 기준

### 기능·안전 필수 테스트

| 테스트 | 기대 결과 |
|---|---|
| 동일 actionId 10회 전송 | 행동·경고·피해 중복 적용 없음 |
| 같은 라운드의 두 공격 | 동일 시작 상태로 정산, 연출 순서와 결과 무관 |
| 체력 0이 되는 첫 연출 | 같은 라운드 상대 공격도 적용 |
| 둘 다 같은 라운드에 HP 0 | 무승부 |
| 모욕·패드립 제출 | 상대 화면·음성·공개 기록에 원문 없음 |
| 무해한 가족 소재 | 단어 포함만으로 반칙 처리하지 않음 |
| 검사 API 시간 초과 | 경고 없이 기본 공격, 원문 비공개 |
| 중계 모델의 욕설 생성 | 대사 대체, 플레이어 경고 없음 |
| 생성 중계가 미구현 효과 주장 | 공개·음성 전에 차단 또는 대체 |
| 이전 경기의 늦은 AI 응답 | 새 경기에 영향 없음 |
| 새로고침·DO 재시작·재접속 | 최신 HP·라운드·경고 복원 |
| 타이머 메시지 중복 실행 | 정산 한 번만 수행 |
| 다른 좌석·방으로 위장 요청 | 권한 거절 |
| TTS 응답 없음 | 무음·자막으로 경기 완료 |
| 모바일 자동 재생 차단 | 재생 버튼·음소거 플레이 제공 |
| AI 예산 상한 도달 | 신규 호출 제한, 정상 안내·기존 경기 대체 처리 |

### 한국어 판정 평가

첫 고정 평가 세트는 50개 사례로 제안한다. 정상 물건 공격, 약점 활용, 능력 밖 주장·시스템 개입, 명확한 욕설·모욕, 무해하지만 오탐하기 쉬운 가족·관용 표현을 각각 포함한다.

안전 판정과 전투 판정의 결과를 구분해 기록한다. 단일 confidence 상한만으로 공개 여부를 결정하지 않는다. 알려진 유해 사례가 그대로 노출되는 상태에서는 자유 입력 공개를 보류하고 준비 기술 모드로 테스트한다. 이 테스트 통과가 모든 우회 공격 방어를 보장하는 것은 아니다.

### 첫 현장 검증 목표

초기 목표는 정상 시작된 경기 10회 중 9회 이상 완료, 양쪽 상태 불일치 0회, 테스트 중 차단 원문 노출 0회다. 재미는 참가자가 ‘다른 무기로 한 판 더’ 하려는지 관찰하고, 첫 가설로 10회 중 5회 이상 재대결 선택을 본다. 소규모 관찰이며 통계적으로 일반화하지 않는다.

기술 지표는 판정 P50·P95, 기본 공격 대체 비율, 음성 제때 재생 비율, 준비 시간, 경기 길이, 경기당 외부 호출 비용이다. 빠르게 보이더라도 대부분 기본 공격으로 대체된다면 자연어 판정 경험은 성공으로 보지 않는다.

| 중계가 길어 템포를 해침 | 공격당 한 문장, 시간 제한, 늦은 음성 폐기 |
| 준비 단계가 길어 이탈 | 작은 설정·기술 수, 제한된 호출, 기본 무기 대체 |
| 콘텐츠가 모욕으로 흐름 | 양방향 검사, 고정 경고, 반복 시 준비 기술 모드 |
| 비용·API 제한으로 행사 중 중단 | 방·세션·전역 예산, 호출 상한, 모델별 중지 스위치 |
| 리소스 제작량이 다시 커짐 | 카드·아이콘·네 연출 고정, 무기별 그림·리깅 제외 |

재미의 우선순위는 **물건의 개성이 살아 있는가 → 타격이 즉시 느껴지는가 → 해설이 장면을 살리는가 → 다시 해보고 싶은가**다. 기능 수를 늘리기 전에 이 네 가지를 확인한다.

## 19. 발표·데모 구성

> “두 분, 아무 물건이나 하나씩 말씀해주세요.”

두 사람의 무기를 입력한다. 게임이 만든 능력과 약점을 짧게 보여준다. 첫 라운드는 준비된 기술로, 다음 라운드는 자유 공격으로 플레이한다. 마지막에는 승패보다 물건의 개성이 드러난 한 장면을 강조한다.

안전 기능은 실제 모욕 문장을 공개 입력해 시연하지 않는다. 개발용 안전 테스트 이벤트로 고정된 경고 화면만 보여준다. 이것이 실시간 필터 판정 시연과 같다고 설명하지 않는다.

마무리 문구는 다음과 같다.

> **“무기마다 콘텐츠를 전부 만들지 않았습니다. 작동하는 규칙과 연출을 만들고, 여러분의 입력이 각자의 싸움을 만들게 했습니다.”**

첫 완성의 기준은 **젖은 양말과 배터리 1% 스마트폰이 서로 다른 기기에서 한 경기를 끝내고, 같은 결과와 중계 장면을 공유하는 것**이다.

# 부록 A. 구현용 내부 데이터 예시

아래는 제품 내부 계약 초안이다. 외부 API의 실제 응답 스키마가 아니다.

```ts
type PlayerSlot = "A" | "B";
type Effectiveness = "LIMITED" | "NORMAL" | "STRONG";
type AnimationType = "DASH" | "PROJECTILE" | "SHOCKWAVE" | "PSYCHIC";
type ModerationDecision = "ALLOW" | "REWRITE" | "FOUL" | "UNCERTAIN";

interface WeaponProfile {
  id: string;
  version: number;
  displayName: string;
  tagline: string;
  capabilities: [string] | [string, string];
  weakness: string;
  visualTag: string; // 검수된 목록으로 제한
  techniques: [PreparedTechnique, PreparedTechnique];
}

interface PreparedTechnique {
  id: string;
  name: string;
  actionText: string;
  animation: AnimationType;
  // 현재 경기·상대·규칙 버전에 맞는 검사·판정 결과를 별도 저장
}

interface JudgeResult {
  moderation: ModerationDecision;
  moderationReason: string; // 허용된 사유 코드
  validity: "VALID" | "OUTSIDE_CAPABILITY" | "SYSTEM_INSTRUCTION";
  effectiveness: Effectiveness;
  animation: AnimationType;
  reasonCode: string; // 허용된 사유 코드
  // 원본 확률·confidence는 평가 로그용으로 별도 보관
}

interface AttackEvent {
  eventId: string;
  actor: PlayerSlot;
  target: PlayerSlot;
  techniqueLabel: string;
  approvedActionText: string;
  effectiveness: Effectiveness;
  damage: 20 | 30 | 40;
  animation: AnimationType;
  cosmeticTags: string[]; // 수치 효과 없음
  reasonCode: string;
  fallbackReason?: string;
}

interface RoundResolved {
  type: "round_resolved";
  matchId: string;
  roundId: number;
  eventSeq: number;
  rulesetVersion: string;
  hpBefore: Record<PlayerSlot, number>;
  hpAfter: Record<PlayerSlot, number>;
  attacks: [AttackEvent, AttackEvent];
  playbackOrder: [PlayerSlot, PlayerSlot];
  resolvedAt: number;
}
```

검증된 객체라도 서버가 다시 범위와 관계를 검사한다. actor/target은 인증 좌석에서 만들고, HP·damage는 서버 규칙으로 생성한다. 표시 문장은 HTML로 삽입하거나 코드로 실행하지 않는다.
